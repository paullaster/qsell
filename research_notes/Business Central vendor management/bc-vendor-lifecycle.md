# Microsoft Dynamics 365 Business Central vendor management

Research snapshot: **2026-11-02**. Primary sources are Microsoft Learn. Source publication dates and observed update dates are noted where available. Business Central is highly localization-dependent: labels, tax treatment, regulatory fields, e-document formats, and payment integrations vary by country/region and installed apps. “Standard” below means documented base application capability, subject to localization and version.

## 1. What is the end-to-end vendor lifecycle, and what is in the vendor master?

### Takeaway
Business Central models vendors as purchasing/payables master records (Vendor Cards), seeded manually, from templates, or from contacts; the master supplies defaults to purchasing documents and payment processing. Vendor data includes general/contact/address details, posting/tax and payment defaults, currency, and separate bank and remit-to address records.

### Cited Findings
- Each supplier used for purchasing must be registered with a vendor card. Vendor cards can be created manually or from reusable vendor templates; templates can carry default values and dimensions. Vendors can also be created from a contact. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors) (Microsoft Learn `ms.date` 2026-08-26; observed `updated_at` 2026-10-01).
- The new-vendor flow allows choosing among multiple templates; if only one template exists, it is used automatically. The document entry flow can also prompt the user to create a new vendor when an unregistered name is entered on a purchase invoice. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors); [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases) (`ms.date` 2026-06-17).
- Vendors can be created from contact records, supporting a relationship-management-to-payables onboarding route. Contact creation is not a third-party supplier portal: the cited docs describe user-led creation. — [Creating a customer, vendor, employee, or bank account from a contact](https://learn.microsoft.com/en-us/dynamics365/business-central/marketing-create-contact-companies#create-a-customer-vendor-employee-or-bank-account-from-a-contact).
- Vendor records hold purchasing defaults; purchase document fields are populated with standard information from the selected vendor. The default is then available for a user to review/override on the document. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Business Central supports multiple vendor remit-to addresses. Users can select the remit-to address per purchase order/invoice; the selected code is carried to the vendor ledger entry when payment journal lines are created (and can be overwritten). — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors).
- Alternative ordering addresses can be set up on a vendor card using **Order Addresses**. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors).
- Vendor bank accounts are separate records accessible from the vendor card. Multiple can be held, and a preferred bank account can be specified for payment journal lines. The bank account card supports payment details including bank branch/account number, SWIFT, and IBAN. — [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts) (`ms.date` 2026-08-17; observed `updated_at` 2026-10-01).
- Sensitive vendor-bank fields can be monitored for changes with notifications, and a built-in **Vendor Bank Account Approval Workflow** template can require review of new vendor bank accounts. — [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts); [Auditing changes](https://learn.microsoft.com/en-us/dynamics365/business-central/across-log-changes) (`ms.date` 2026-06-17).
- Vendor template and card management includes standard registration, apply/save template, contact details, ordering/remit-to addresses, payment priorities and supplier agreements. A vendor with posted transactions cannot normally be deleted because of audit/ledger history; Microsoft advises contacting a partner if deletion of a vendor with ledger entries is required. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors).

### Inferences
- A robust onboarding process should treat the vendor card as a controlled master-data record and separately capture payment destinations, tax identifiers, and addresses, because those data are maintained in connected records/fields with distinct controls.
- Template-based classification can reduce inconsistent master data, but Microsoft docs do not describe an out-of-box supplier self-service onboarding portal, external identity checks, or mandated due-diligence workflow across all regions.

### Gaps
- The accessed vendor documentation does not provide a full, definitive field-by-field card schema for every localization or extension; page personalization and local versions can expose additional fields.
- No universal onboarding approval is documented for the complete vendor card in the sources accessed. The specific bank-account approval workflow is documented.

## 2. How are defaults, posting groups, payment terms/methods, currency, and tax configured?

### Takeaway
Vendor defaults are backed by shared setup tables, not free-form accounting logic: vendor posting groups map payables to G/L, general business/product combinations route purchase values, and VAT/tax business-product combinations determine tax calculation and posting. Currency, payment terms, and methods are master-data references; country localization determines which tax model and fields apply.

### Cited Findings
- **Vendor Posting Groups** determine G/L accounts for payables, service charges, and payment discounts. General Business Posting Groups classify who the company buys from; General Product Posting Groups classify what it buys; General Posting Setup maps combinations to G/L accounts. — [Posting group setup](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-posting-groups) (`ms.date` 2025-08-13; observed update 2025-10-01).
- Tax posting groups are separate: Tax Business Posting Groups describe supplier/customer market; Tax Product Posting Groups describe goods/services; Tax Posting Setup combines them to determine tax calculations/accounts. Where applicable, VAT uses corresponding VAT business/product posting groups and VAT posting setup. — [Posting group setup](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-posting-groups); [Set up value-added tax](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat) (`ms.date` 2026-04-07).
- Vendor records may receive default VAT business posting groups through mappings from general business posting groups or vendor templates. The VAT business group combines with the product group on purchase lines to determine VAT percentage, calculation type, and posting accounts. — [Set up value-added tax](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat).
- VAT registration number format checks can be configured by country/region. This validates formatting, and Microsoft also documents an EU VAT Registration Number Validation service for checking eligible EU numbers. Local tax rules and local functionality apply; the general VAT guide is not a universal tax-compliance specification. — [Set up value-added tax](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat); [Verify VAT registration numbers](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-how-validate-vat-registration-number).
- Vendor-specific fields surfaced by the standard v2.0 vendor API include `taxRegistrationNumber`, `taxLiable`, `currencyId`/`currencyCode`, `paymentTermsId`, `paymentMethodId`, and `blocked`; its published object does not expose the entire vendor-card schema. — [Vendor resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendor) (`ms.date` 2026-08-21; observed `updated_at` 2026-08-24).
- Currency is configured centrally and may be assigned as the vendor's default. A blank document currency means local currency. Foreign-currency documents are converted to LCY at the posting-date rate; vendor and purchase entries retain currency information, and later exchange-rate adjustment/payment can create unrealized and realized gains/losses. — [Currencies in Business Central](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-currencies) (`ms.date` 2024-08-09; observed update 2025-05-07).
- Purchasing setup includes **Purchases & Payables Setup**, number series, discount/tax handling and policy settings; payment methods and currencies are configured as part of finance setup. — [Overview of tasks to set up purchasing](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-setup-purchasing) (`ms.date` 2025-10-03; observed update 2025-10-22).
- The v2.0 API makes payment terms and method navigations available from a vendor resource, consistent with referenced setup entities rather than arbitrary per-document strings. — [Vendor resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendor).
- Invoice amounts and due/payment activation flow from purchase posting and the vendor's payment terms; vendor invoice prices can display inclusive or exclusive of tax according to vendor setup. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Alternative vendor posting groups can be allowed at setup/card level; the chosen group is copied to posted documents/journals and drives the payable G/L account. — [Posting group setup](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-posting-groups).

### Inferences
- Posting-group governance is financially material: an incorrect vendor group can direct payables to the wrong control account, while business/product combinations affect purchasing expense/inventory and tax treatment.
- Multi-currency payable balances require FX-rate maintenance and valuation policy, not just a currency code on the vendor.

### Gaps
- Exact card field availability and labels depend on localized application version; the sources do not define one globally identical tax-registration model (VAT/GST/sales tax/withholding) for every country.
- The cited standard API vendor schema does not show bank accounts, remit-to addresses, general/vendor posting-group IDs, or all tax setup dimensions in its published property list; assess endpoint coverage by API/version before integration design.

## 3. How do purchasing documents, receipts, invoices, and posting connect to vendors?

### Takeaway
Purchasing uses quotes/orders/invoices/credit memos and journals against the vendor master. Purchase orders support staged/partial receipt and invoice posting; posting produces both vendor subledger and G/L entries alongside inventory/resource/tax effects, while posted documents remain auditable and can be corrected or reversed through defined processes.

### Cited Findings
- A purchase invoice or order records purchase cost and accounts payable. Vendor selection fills default fields; users enter lines (items, resources, G/L accounts as applicable) and post when goods/services are received. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases) (`ms.date` 2026-06-17).
- Purchase orders are appropriate where partial receipts are needed. Users set **Qty. to Receive** and post receipts; orders may be partially received and invoiced, or receipt and invoice can be posted together. An item purchase invoice cannot be posted from an order before receipt (unless receive and invoice together). — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Posting a purchase updates vendor account, G/L, and applicable item/resource ledgers. It creates a Vendor Ledger Entry, G/L entries including the relevant payables account, and potentially VAT/tax and discount entries; purchase receipt/invoice history is recorded. **Preview Posting** previews the expected entries. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Vendor external document numbers can be required via **Ext. Doc. No. Mandatory** and searched on posted entries; vendor invoice/order/credit memo number fields and relevant journal lines are covered. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases); [Overview of tasks to set up purchasing](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-setup-purchasing).
- Over-receipt tolerances can be configured through over-receipt codes assigned to vendors/items; a workflow can require approval. Business Central does not automatically settle the financial impact of excess receipts; supplier agreement/invoice handling remains necessary. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Posted unpaid purchase invoices can be corrected/cancelled; where payment has been processed, a purchase credit memo is the documented route for reversal. — [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Vendor-specific self-billing is documented in the latest vendor registration guide: a vendor can have a self-billing agreement and invoice number series, with the vendor-level series taking precedence over the global series. The guide includes Danish-specific caveats, including digital voucher and e-document restrictions. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors) (`ms.date` 2026-08-26).
- As of 2026 release wave 2 / update 29.0, **Improve purchase order matching in Payables Agent** is listed as general availability. The same version list includes other agent capabilities, but does not imply an autonomous agent replaces the standard purchasing controls or is enabled in every tenant. — [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0) (`ms.date` 2026-09-29; published table marks feature GA).

### Inferences
- A dependable three-way match process (order, receipt, vendor invoice) combines standard purchase order receipt/invoice tracking with human or agent matching; the cited sources do not establish a universal mandatory tolerance/matching rule.
- Vendor invoice number capture and duplicate prevention controls should be explicitly configured (including mandatory external document number) and tested with actual posting workflows.

### Gaps
- Purchase approval policy details vary by workflow configuration and extensions; this review did not verify a standard automatic three-way-match engine’s precise tolerances for all document types/localizations.

## 4. How are vendor ledger/payables, payment execution, blocking and archival handled?

### Takeaway
Vendor invoices create open vendor ledger entries/payables; payments are proposed or entered in payment journals, exported or issued by check, then applied/reconciled to close the open entries. Vendor blocking is represented in the API as a status enumeration, while record deletion is restricted by posted history; vendor ledger compression/archive concerns historical ledger entries, not vendor-master deletion.

### Cited Findings
- The Payment Journal supports **Suggest Vendor Payments**, due-date/discount/liquidity criteria, checks, electronic bank-file export, and manual payment processing. Payments must be applied to related open vendor ledger entries, manually or through imported bank statement/payment reconciliation. — [Overview of tasks to manage payments to vendors](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-make-payments) (`ms.date` 2025-06-15; observed update 2025-06-18); [Manage accounts payable](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-manage-payables) (`ms.date` 2025-06-17; observed update 2026-06-02).
- A vendor's preferred bank account is available for payment journal lines; bank export/SEPA/payment conversion features can use vendor bank data, subject to country and extension setup. — [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts); [Overview of tasks to manage payments to vendors](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-make-payments).
- Vendor bank details are sensitive and Microsoft explicitly recommends monitoring changes; for IBAN/account fields, historic credit transfer register entries retain the recipient details used at creation even if the vendor account is later edited. — [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts); [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors).
- The standard vendor API's `blocked` property has type `NAV.vendorBlocked`; the documented values are blank, `Payment`, or `All`. This supports restricting payments or all transactions at the vendor level; the operational UI and exact posting behavior should be validated against the target build/localization. — [Vendor resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendor) (`ms.date` 2026-08-21).
- A vendor with posted transactions cannot normally be deleted because ledger entries may be needed for audit. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors).
- Data Archive is a preinstalled extension that archives records deleted by date-compression batch jobs, including **Date Compress Vendor Ledger**; it is for ledger/history data archiving, not a vendor-card lifecycle status. Archive holds up to 10,000 records per table per archive segment and can be exported as Excel/CSV. — [The Data Archive Extension](https://learn.microsoft.com/en-us/dynamics365/business-central/admin-archive-data) (`ms.date` 2023-01-30; observed update 2026-01-19).
- Payables analytics include Aged Payables (back-dated), Detailed Vendor Ledger Entries, data analysis of Vendor Ledger Entries, aged payables Excel, Vendor Detail Trial Balance, Vendor Balance to Date, Vendor Trial Balance, open purchase order summaries/details, Purchase Statistics and Vendor/Item Purchases. Microsoft marks some older reports (including Vendor List, Vendor Summary Aging, Payments on Hold and Aged Accounts Payable) as legacy and links alternatives. — [Accounts payables analytics](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-reports) (`ms.date` 2024-07-15; observed update 2025-05-07).

### Inferences
- For an inactive supplier, blocking is generally safer than attempting to delete a vendor with ledger history; the API documentation confirms block values, though exact UI controls should be confirmed in the tenant.
- Bank-detail change monitoring and approval provide an important control point against payment redirection; configure notifications, access permissions, and review responsibilities together.

### Gaps
- A single dedicated Microsoft Learn procedure for vendor-master block/unblock behavior was not found in the accessed pages. The API enum provides the supported state terms, but does not fully describe every action/page and posting validation.
- Date compression is irreversible at the source ledger level unless archive is enabled; exact retention/legal hold policies remain organization and jurisdiction-specific.

## 5. What approval, change control, reports, and security controls exist?

### Takeaway
Business Central provides configurable workflow events/responses, approval users/groups and notifications; specific approval templates exist for vendor bank accounts and over-receipts. Change Log and sensitive-field monitoring support audit, but logging is selective and has performance/storage costs, so controls must be deliberately configured.

### Cited Findings
- Workflows connect tasks across users and can include approval requests, record creation and system tasks. Workflow lines pair supported events/conditions with responses/options; unsupported events/responses require Power Automate, an AppSource app, or AL customization. — [Set up approval workflows](https://learn.microsoft.com/en-us/dynamics365/business-central/across-set-up-workflows) (`ms.date` 2026-06-17).
- The workflow setup sequence includes workflow users/groups, approval users, notifications, and workflow definition; templates can be used and exported/imported. — [Set up approval workflows](https://learn.microsoft.com/en-us/dynamics365/business-central/across-set-up-workflows).
- The **Vendor Bank Account Approval Workflow** template can require review of new bank accounts. Over-receipt codes also offer an **Approval Required** option for approval workflow handling. — [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts); [Record purchases with purchase invoices](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-record-purchases).
- Change Log can track selected table/field direct modifications, recording old/new values, user and timestamp. Microsoft cautions that tracking can reduce performance and increase database size; recommend limiting tables/fields and avoiding all-fields logging. — [Auditing changes](https://learn.microsoft.com/en-us/dynamics365/business-central/across-log-changes) (`ms.date` 2026-06-17).
- Sensitive field monitoring can notify by email when monitored values change (example: IBAN); field monitoring has a separate monitored-fields log and can emit telemetry. — [Auditing changes](https://learn.microsoft.com/en-us/dynamics365/business-central/across-log-changes).
- The v29 update adds GA avatar display for record creators/modifiers in lists and marks **Use system audit fields in analysis mode and in profiles** as GA; this can improve visibility of creator/modifier metadata, not replace the detailed change log. — [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0) (`ms.date` 2026-09-29).
- Standard AP reporting and analysis includes Power BI, Excel, data analysis, balance aging, detail/trial balances and purchase commitments; several old report IDs are explicitly identified as legacy. — [Accounts payables analytics](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-reports).

### Inferences
- Vendor master-change control is not a single switch: combine least privilege, selected change log fields, monitored-field alerts for sensitive banking/tax identifiers, and approval workflow where the scenario is supported.
- Approvals should be applied to risk-sensitive updates (especially payment destinations and financial defaults) while preserving a practical exception path and recorded rationale.

### Gaps
- The accessed official materials do not say that all vendor-card fields support a built-in approval workflow. The documented bank-account approval workflow should not be generalized to all vendor master edits without testing or extension design.
- Change Log and sensitive-field monitoring have different coverage/behavior; confirm table/field availability and session-refresh requirements in the target tenant.

## 6. What APIs, integrations, standard features, and extensions apply? What changed from v26 to v29?

### Takeaway
The standard REST API v2.0 exposes vendor CRUD and a useful but partial vendor schema; extensions/custom APIs are needed when a required field or related entity is not published. Version 26 begins 2025 wave 1; version 29 begins 2026 wave 2 and is documented as available to new online customers on the research date. No dedicated new vendor master-management capability is listed in the 29.0 change table; relevant procurement/payables improvements include agent-assisted PO matching, and v29 also lists vendor-specific self-billing number series as preview.

### Cited Findings
- Business Central API v2.0 is a standard REST API for Connect apps. APIs are enabled by default online. Microsoft states that standard APIs cannot currently be extended with additional fields; where necessary, copy the API AL code and build a custom API. — [API (v2.0) for Business Central](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/) (`ms.date` 2026-08-10; observed update 2026-10-01).
- The standard vendor resource supports GET/POST/PATCH/DELETE and navigations including currency, payment term, payment method, default dimensions, aged accounts payable, contact information and document attachments. Its fields include name/number, postal/contact details, tax registration number, currency, terms/method, tax liable, blocked status, balance and last-modified time. — [Vendor resource type](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/api-reference/v2.0/resources/dynamics_vendor) (`ms.date` 2026-08-21).
- Vendor registration documentation describes Outlook-based vendor registration/business interaction and receiving/incoming document processing through purchasing setup. Incoming e-documents, bank file/payment conversion, Power Automate, and local tax/e-document capabilities connect through standard framework, localization, or extensions. — [Overview of tasks to set up purchasing](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-setup-purchasing); [Manage accounts payable](https://learn.microsoft.com/en-us/dynamics365/business-central/payables-manage-payables).
- **Version 26.0** is the 2025 release wave 1 update. Microsoft identifies purchase order line matching with Copilot and e-document developments among its new features. 26.0 online customers were scheduled for managed major updates; the release doc says new online customers receive 26.0 at launch. — [What's New/Changed in update 26.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-26-0) (`ms.date` 2025-04-24; doc updated 2026-02-26).
- The current versioned documentation accessed for this research identifies **update 29.0 / 2026 release wave 2**, published 2026-09-29. It lists new online customers automatically receiving v29.0 and existing customers being notified; the five-month update period ends February 2027. As-of 2026-11-02 this is the latest published version in the accessed official “What’s New” series. — [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0).
- v29 lists **Improve purchase order matching in Payables Agent** as generally available. It lists **Vendor specific number series for Self-billing Invoices** under Finance as **Public preview** (Roadmap ID 573307); do not describe that feature as GA solely because it appears in release information. — [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0).
- The vendor registration Learn article (updated in 2026) already documents vendor-specific self-billing invoice number series in its user steps. This is a documentation timing/availability nuance relative to the v29 page's roadmap table marking the feature preview: feature rollout, availability channel, localization and tenant version can differ. Verify the tenant and feature status rather than assuming universal availability. — [Register a new vendor](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-register-new-vendors); [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0).
- Starting September 2026, Microsoft says it stops publishing new release plans and will publish new capabilities on the AI at Work roadmap; previous release plans remain available as historical reference. The 29.0 What's New page remains the cited version-specific source for this snapshot. — [What's New/Changed in update 29.0](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/whatsnew/whatsnew-update-29-0).
- Standard-vs-extension boundaries: the Data Archive is a preinstalled extension; AMC Banking and some SEPA/payment conversion functionality are extensions/service-dependent; VAT and tax rules are local-version-dependent; workflow scenarios beyond shipped events/responses need Power Automate, Marketplace apps, or AL customization. — [Data Archive Extension](https://learn.microsoft.com/en-us/dynamics365/business-central/admin-archive-data); [Set up vendor bank accounts](https://learn.microsoft.com/en-us/dynamics365/business-central/purchasing-how-set-up-vendors-bank-accounts); [Set up approval workflows](https://learn.microsoft.com/en-us/dynamics365/business-central/across-set-up-workflows); [Set up value-added tax](https://learn.microsoft.com/en-us/dynamics365/business-central/finance-setup-vat).

### Inferences
- Integrations should use the standard vendor resource for common vendor identity and payment defaults but model bank accounts, regulatory data, approval states, and unsupported card fields explicitly after inspecting API Overview and the target environment's published endpoints.
- For version upgrades, validate API fields, workflows, report IDs, localization, and preview/GA status in the exact environment; Learn pages can be updated independently of an organization's deployment cadence.
- The base product supplies purchasing-to-payables lifecycle, audit hooks, payments and reporting; onboarding portals, automated supplier verification, broader supplier risk controls, e-invoice network coverage, and specific bank/local payment connectors commonly require additional configuration or extensions.

### Gaps
- Microsoft’s API v2.0 vendor page gives a versioned resource schema but does not provide a full mapping for every related vendor bank-account/contact/remit-to entity or every app/localization API in this research snapshot.
- Microsoft does not guarantee one release date for v29 in every tenant: staged update windows and administrator scheduling affect actual deployed versions.
- The public release/What's New page's preview designation and the updated how-to article's present-tense procedure for vendor-specific self-billing series are not perfectly aligned. Confirm in-product Feature Management/current release notes before reliance.
