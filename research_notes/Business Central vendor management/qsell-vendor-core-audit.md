# qsell vendor management domain — read-only implementation audit

## Scope and audit method

Read-only source review of vendor master/onboarding through procurement and accounts payable, including Drizzle schema and migrations, service/action entry points, permissions evidence, relevant tests, and `docs/architecture/vendor-management-module.md`. No code or database changes were made and no test suite was run. Evidence below is repository evidence; paths are relative to the repository root and line references refer to the inspected snapshot. Integration tests explicitly skip without `TEST_DATABASE_URL`; e2e execution requires its separate configured environment.

The project constraints in `docs/PROJECT_RULES.md` guided the audit: server-side permission checks, company-scoped queries, validated server inputs, session-derived portal vendor identity, transactionality, idempotency, immutable history, paged server lists, Autocomplete rather than native selects, responsive UX, and unit/integration/API/e2e pyramid expectations. Claims in design-document as-built sections are corroborative documentation, not independent proof of runtime behavior.

## Overall implementation status

### Takeaway

This is a substantial, unusually well-structured vendor and procure-to-pay implementation: the master/onboarding, qualification, RFQ/quote, PO/receipt, supplier invoice, AP posting/payments, refunds and bank change controls have real services, migrations, and meaningful database-backed tests. It is not equivalent to the entire approved design: several large workflows remain deliberately absent, simplified, or are explicitly identified as deferred in the architecture document; the document's opening “Nothing here is built yet” is stale and contradicted by its detailed V-0 onward as-built sections.

### Evidence by lifecycle

#### Vendor record, lifecycle, profile, contacts/addresses, bank and documents

- `src/server/domains/vendors/service.ts` (`VendorService.createByStaff`, `activateIn`, `registerBusiness`, `list`, `get`) implements company-owned creation, number assignment on activation, registration/owner link, audit event writing, and keyset paging/search over legal/trading name, number, email and tax ID. List action `src/server/domains/vendors/actions.ts` (`listVendorsAction`, `vendorDetailAction`, `createVendorAction`) enters finance `run(...)` with explicit permissions and takes company from context.
- `drizzle/0072_vendor_foundation.sql` creates vendor state/block checks, company foreign key, unique company number/tax ID, company/status/email indexes, portal-user ownership constraints, append-only vendor events and vendor ledger idempotency uniqueness. `src/server/domains/vendors/lifecycle-service.ts` implements suspend/reinstate, payment/all blocking, archive/restore with reason events and balance/pending-bank/review checks. Archive balance is checked before the locked state change, however: concurrent creation of payable exposure deserves scrutiny; the check and state transition are not one transaction/lock across the ledger.
- `src/server/domains/vendors/profile-service.ts` (`VendorProfileService`) implements section saves, completeness, owner/role restrictions, profile snapshot submission, sealed director IDs and bank numbers, contacts, references, bank setup, document replacement and event history. Profile loading scopes the vendor row by company, and portal writes use actor vendor ID; data tables for child profile records generally scope by vendor ID. `drizzle/0073_vendor_profile.sql` adds contacts with one-primary partial unique index, addresses as vendor columns (physical + postal), bank status and sealed account/hash/last-four, profile version snapshots, document type/document/file tables and guards against editing bank details, profile snapshots and uploaded file bytes.
- Profile test coverage is substantive in `src/server/domains/vendors/vendor-profile.integration.test.ts`: role-section restrictions, tax-ID uniqueness, sealed values, DB immutability, cross-vendor child-record isolation, file content/name validation, date/expiry validation, replacement history, frozen profile, verified-document activation, revision/rejection and event attribution. `e2e/vendor-onboarding.spec.ts` covers an actual portal-to-staff review journey (design doc §26 test inventory).
- Limitation: “addresses” are not an independently modelled multi-address book; the schema stores one physical and one postal set on `vendors`. Contacts are replaced as a whole via `saveContacts`; history records section saved, not before/after field diffs. `saveReferences` similarly deletes/reinserts records. Bank status history is auditable, but sensitive values are intentionally not in vendor profile snapshots.
- File route authorization is backed by `portal-isolation.test.ts` (source-level action/route tripwire) and integration tests; file bytes are in DB and supported MIME types are constrained. Size limits differ in docs vs migration (`0073_vendor_profile.sql` says 25 MiB; architecture §26 says 10 MB)—resolve documentation/runtime policy by inspecting `src/server/domains/vendors/file-store.ts` before treating either figure as authoritative.
- Controlled bank change is implemented in `bank-change-service.ts` and described in architecture §27: callback evidence, four-eyes constraint, cool-off, atomic promotion, pending uniqueness, sealed account details. E2E/integration tests are named `vendor-controls.spec.ts` and `vendor-controls.integration.test.ts`.

#### Qualification and documents/compliance

- Architecture §28 (V-2) documents built category tree, questionnaire, multiple-category applications, scoring/decision, validity, document gates, renewal prefilling, automatic document-driven suspension/restoration, and category qualification query used by RFQ/PO. Source/test file inventory includes `prequal-service.ts`, `prequal-review-service.ts`, `prequal-actions.ts`, `prequal-portal-actions.ts`, `prequalification.integration.test.ts`, `src/lib/prequalification.test.ts` and `e2e/prequalification.spec.ts`.
- Limitations are explicitly stated: file-question kind is not built; qualification decisions are not connected to approvals engine `vendor.prequalification` (architecture §28); country-specific tax pattern is not wired (architecture §27). Blocking document state is stored and expiry worker integrated; its category consequence only exists once qualification exists.

#### RFQ, quote and purchase order

- RFQ has actual service/action/schema/test surfaces (`rfq-service.ts`, `rfq-evaluation-service.ts`, `rfq-actions.ts`, `rfq.integration.test.ts`, `e2e/vendors`-adjacent `vendor-pickers.spec.ts`; migration `0076_rfq.sql`). Architecture §29 identifies missing request/quote attachments, weighted-score evaluation, foreign-currency quotes/comparison conversion, RFQ issue/award approvals, and award-to-PO conversion; branch/dimensions also deferred. These are not minor UI omissions: they leave documented tender controls/traceability incomplete.
- POs, qualification gates, approval and vendor confirmation are implemented (`po-service.ts`, `po-actions`/portal actions, `po.integration.test.ts`, `e2e/vendor-contract.spec.ts` etc.; `drizzle/0077_purchase_orders.sql`). Architecture's later as-built sections should be read with explicit deferral tables. Advance-payment invoice exception is exercised by `invoice.integration.test.ts` lines 463–499. RGN posting, quantity acceptance and invoice-linking are present in `rgn-service.ts` and `rgn.integration.test.ts`.
- Supplier invoice database constraints and lifecycle are especially strong: `drizzle/0080_supplier_invoices.sql` enforces invoice number uniqueness excluding closed/rejected, company queue indexes, immutable posted invoices/events, state checks, posted link requirement, four-eyes check, quantity caps and guards against post-submission vendor line edits. `invoice-actions.ts` applies explicit permissions per action. `invoice.integration.test.ts` exercises duplicates, session/vendor isolation, server-calculated totals, proof-file ownership, blocked vendor, recall/pickup race, RGN linking and held quantity, match overrides with reason, return/revision, four-eyes approval both service and DB, atomic posting to AP/GL, failure rollback, immutable posted records and advance rule.
- Caveat: migration supports exactly one `po_id` per supplier invoice (`0080_supplier_invoices.sql`), whereas architecture §11.2 and §11.4 contemplate multiple POs; this is a real model/design mismatch. Invoices are PO-required in current schema (`po_id NOT NULL`, invoice line `po_line_id NOT NULL`), so free-standing expense-vendor invoices described in design are not supported by this path. Documented service acceptance/2-way matching for services is simplified: invoice lines still link PO lines and the RGN integration test expects receipt/acceptance. No API/e2e-specific supplier-invoice coverage was verified in this audit beyond listed database and e2e filenames.

#### Contracts

- `src/server/domains/vendors/contract-service.ts` implements blanket-contract draft, creator submit, four-eyes approval, close/cancel, usage and events; approved contracts described as immutable, with order consumption tracked from purchase orders. Migration `0093_vendor_contracts.sql`, `contract.integration.test.ts`, `vendor-contract.spec.ts` exist.
- Scope limitation: architecture §22's exclusions (and §773) explicitly describe contracts/blanket orders as designed for and “not built in V-0..V-8”, which conflicts with the present contract service and test files; confirm the relevant later as-built note and current navigation before declaring this feature complete. Code service shows core staff workflow, but audit did not establish vendor-side contract acceptance, amendments/versioning, expiry worker or full commercial lifecycle.

#### Invoices, payables, payments, payment batches and refunds

- AP invoice posting has a dedicated `invoice-posting-service.ts`, and the integration test proves posted purchase invoice, vendor ledger and GL journal together, PO/RGN quantities updated, posting retry rejected, and immutable posting. Ledger foundation migration `0072_vendor_foundation.sql` has unique company/idempotency key and unique external invoice number per vendor; triggers protect immutable economic fields and append-only detail/event records. Finance ownership division is clearly described in architecture §§4 and 12.
- Payment services are present (`payment-service.ts`, `payment-run-service.ts`, `advance-service.ts`, `payables-fx-service.ts`) with `payment.integration.test.ts`, `payment-run.integration.test.ts`, `vendor-payout.integration.test.ts`, FX/statement tests; migrations `0081_vendor_payments.sql`, `0082_vendor_payment_batches.sql`, `0096_vendor_foreign_currency.sql`, `0097_payables_revaluations.sql`. Refund workflow is separate and genuinely four-eyes: `refund-service.ts` / `refund-actions.ts`, migration `0089_vendor_refunds.sql`, `refund.integration.test.ts` asserts refund request/post segregation, bounds against available credit, bank/GL/ledger consistency, reversal and immutability.
- Audit did not verify each payment/provider failure/idempotency branch, batch concurrency, payment destination selection at the final posting boundary, or outbox delivery semantics from source. Tests prove important happy and refusal paths, not all provider retry/duplicate callback or simultaneous voucher races. Treat those as unproven, not necessarily absent.
- Refunds are repayment of vendor credit/on-account balances, not customer-style refunds to the vendor. Architecture claims fuller ledger applications/discount/FX in V-7; check test inventory (`statement-payment.integration.test.ts`, `vendor-fx.integration.test.ts`) for those flows.

#### Audit/history, permissions, tenancy, search/list UX and idempotency

- `src/server/domains/vendors/portal-access.ts` (`findPortalAccess`) derives portal vendor/role from active `vendor_users`, denies archived vendors, and permits payment-blocked access. `portal-isolation.test.ts` requires portal action wrappers and vendor routes to use portal runner/session. This tests source shape, not authorization behavior; business isolation is additionally tested in profile and invoice integration tests.
- Staff actions typically use finance `run(permission, ...)` with server-derived company and actor; portal entrypoints use `portal-runner.ts`. `invoice-actions.ts` demonstrates fine-grained permissions and separates approval permission from linked/matched staff. Staff detail action checks ledger visibility separately. Relying on route/proxy alone would not be enough, but server runners/actions are present.
- Tenancy: main vendor list/detail and document types scope by company; most business records carry `company_id` and services filter by context. Child profile tables key from vendor and their parent vendor ownership is checked. Potential schema weakness: multiple relations are separate FKs without composite company/vendor constraints, so correctness depends on service filters/ownership validation; audit found no RLS policy evidence. In `VendorProfileService.load`, once vendor is company-scoped, related rows query by vendor ID (appropriately unique parent ID). In `contract-service.ts`, vendor and category are separately checked against company before insert.
- Search/list UX: `VendorService.list` uses server-side escaped `ILIKE`, company/status filter, capped page size and microsecond-safe `(created_at,id)` cursor; `e2e/vendors.spec.ts` checks search, no native `<select>`, modal route, phone overflow and 404. Contracts list in `contract-service.ts` is offset-free but hard-capped at 200 and ordered newest; unlike vendors, it has no cursor and no query text. Inspect other module lists individually; there is not a universal paging guarantee.
- Idempotency: vendor ledger has DB unique idempotency key; event/ledger methods and invoice posting transactions add further duplicate guards. `VendorService.createByStaff` maps all unique violations to tax-ID duplicate, which can misreport a different uniqueness collision. Not every domain write exposes a request idempotency token; avoid inferring end-to-end request idempotency from ledger uniqueness alone.
- Audit coverage: `vendor_events`, `supplier_invoice_events`, contract/prequal/RFQ histories and immutable finance records capture substantial trace. Vendor `get` exposes last 100 events (`service.ts`), so history UI is bounded and lacks cursor in that method. Some child data changes are whole-list replacements, so event payloads do not reconstruct exact prior contact/reference values. Confirm whether any state mutation path lacks event in each domain; design-level “every action” is broader than proven tests.

### Test evidence: what is and is not proven

- Strong: DB-backed integration tests test migrations/constraints as well as service logic, often directly attempt tampering; core examples `vendor-profile.integration.test.ts`, `invoice.integration.test.ts`, `refund.integration.test.ts`, `vendor-controls.integration.test.ts`, `prequalification.integration.test.ts`, `rfq.integration.test.ts`, `po.integration.test.ts`, `rgn.integration.test.ts`, payment/contract suites. Unit tests cover pure validation/formula helpers. Playwright suites cover desktop and phone journeys, but only selected critical paths.
- `e2e/vendors.spec.ts` proves admin vendor list/search/create/modal, activate, registration/email verification, role redirects and no horizontal overflow—not profile review, qualification, quote comparison, PO/receiving, AP payment, refund or full audit UX. Dedicated E2E suites exist for onboarding, controls, qualification, scorecard, contract, refund, FX, M-Pesa destination, reports and pickers; existence is not proof of every path.
- Integration suites are skipped when `TEST_DATABASE_URL` is absent (`describe.skipIf(!has(url))` in inspected tests). The repository instructions require running with migration-built fresh DBs and separate e2e DB. This audit did not execute tests; pass status is not asserted.
- No specific API test suite for vendor endpoints was located/verified in examined file inventory. Project rule §6 requires unit, integration, API and e2e for every feature. This indicates a test-pyramid evidence gap unless API coverage is organized elsewhere (search/repository inventory did not establish it).
- `portal-isolation.test.ts` is a regex/source scan; it can catch obvious unsafe signatures but cannot prove a role is authorized correctly, query scoping is correct, or races are safe. Behavioral DB tests compensate partially.

### Documentation consistency / explicit gaps

- Architecture doc opening §0 / line 9 says “Nothing here is built yet”; later §§25–29 and 27–28 provide as-built evidence through qualification and RFQ. Update should be considered because it misleads audit readers; no edits made.
- §29 explicitly lists RFQ gaps above. §773 lists landed costs, blanket contracts, requisitions, scorecards beyond measured ones, EDI and purchase e-invoicing as not built; actual domain files now include service/test surfaces for landed cost, requisitions, scorecards, EDI and contracts, so these statements are likely stale or describe the state at a prior cut. Verify later as-built sections and route visibility before relying on the table.
- Vendor-specific lifecycle docs claim comprehensive states, support for many capabilities, and every action event; code confirms much but not all. This is an implementation audit, not a validation of every administrative route or migration constraint; file inventory and spot-checks are not exhaustive enough to pronounce all feature paths complete.

### Priority gaps / follow-up audit targets

1. Resolve documentation drift (opening “nothing built”, deferred list vs later services) and publish a current feature matrix with unsupported flows explicit.
2. Decide whether supplier invoice multi-PO and expense/free-line invoice workflows are requirements; schema currently prevents both although design promises them.
3. Complete/verify RFQ addenda/attachments, weighted evaluation, FX comparison, approvals, award-to-PO conversion, branch/dimensions and cross-document traceability.
4. Verify concurrency/idempotency on payment voucher creation, batch execution, provider callbacks, refunds, profile submission versioning, archive-vs-new-payable and document expiry/reminder claims; add API-level tests where absent.
5. Audit transactional event completeness and immutable-history semantics for contacts, addresses, references, qualification, RFQ, PO, contracts and payment actions; test hostile cross-company IDs and unauthorized permissions at action/API boundary.
6. Reconcile file-size policy (migration 25 MiB vs architecture 10 MB) and determine actual `file-store.ts` cap.
