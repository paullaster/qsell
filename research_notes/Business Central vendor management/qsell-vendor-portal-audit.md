# Qsell vendor onboarding, invitation and portal audit

Audit date: 2026-11-02. Scope: repository source, migrations, tests, environment example and vendor-management architecture notes. Read-only audit; no application code was changed.

## Does invitation, delivery, token redemption, user creation and login work, and why might vendors receive test/demo emails?

### Takeaway

Invitation-led access is already substantially implemented for both a staff-invited vendor owner and an owner-invited colleague; there is also a separate public self-registration path, contrary to the preferred invitation-led policy. The repository proves the email content and send-adapter behavior, but cannot establish what a deployed environment actually sends: the most concrete source-level cause of “test/demo emails” is that the default email driver is the console adapter, while SMTP configuration is environment-dependent.

### Cited Findings

- `VendorInvitationService.inviteOwner` checks company ownership, archived status, and absence of an active owner; the portal owner flow only permits `finance`, `sales`, or `readonly` colleagues. Both converge on `create` in [invitation-service.ts](../../../../src/server/domains/vendors/invitation-service.ts#L35-L83).
- `create` normalizes email, validates name/email, caps active linked users at ten, and creates a `vendor` user with an unknown random password and `emailVerified: false`. It inserts `vendor_users` plus a `portal_user_invited` event transactionally, removing the unverified user on link failure. If `findByEmail` already finds any account, it silently returns without associating that account or sending an invitation; the public response is intentionally non-enumerating. (Same source, lines 35–54.)
- The link uses an auth token with purpose `password_reset`, 7-day TTL, and `/reset-password?token=...`. The common reset page accepts that token; `AccountService.resetPassword` consumes only a valid, unused, unexpired `password_reset` token and changes the password while verifying the email in one transaction. ( [invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L56-L59), [account-service.ts](../../../src/server/domains/auth/account-service.ts#L103-L117), [reset-password/page.tsx](../../../app/reset-password/page.tsx#L9-L23) ).
- Auth tokens are 32 random bytes, persisted as SHA-256 hashes, atomically consumed, and outstanding same-purpose tokens revoked when a new token is issued; resend therefore invalidates the earlier outstanding link. ([token-repository.ts](../../../src/server/domains/auth/token-repository.ts#L11-L16), [token-repository.ts](../../../src/server/domains/auth/token-repository.ts#L34-L51), [token-repository.ts](../../../src/server/domains/auth/token-repository.ts#L74-L113)).
- The invitation integration test follows the delivered link through password set, confirms `role === 'vendor'`, database-derived portal access and one-time redemption; additional cases cover existing-address non-disclosure, role checks, resend and cancellation/removal. ([vendor-controls.integration.test.ts](../../../src/server/domains/vendors/vendor-controls.integration.test.ts#L320-L369)).
- `VendorNotifier.invitation` renders a branded “Join [business]” message, role, 7-day note and password CTA; all vendor templates use company trading name and configured public base URL, not request Host. Sending errors are caught/logged and do not roll back persisted invitation state. ([notifier.ts](../../../src/server/domains/vendors/notifier.ts#L19-L48), [notifier.ts](../../../src/server/domains/vendors/notifier.ts#L174-L184)).
- The container selects SMTP only when `EMAIL_DRIVER` is explicitly `smtp`; every other or absent value selects `ConsoleEmailAdapter`. ([container.ts](../../../src/server/di/container.ts#L310-L321)). The console adapter logs recipient, subject and a body preview and returns a successful-looking adapter result; it does not deliver mail. SMTP sender defaults to `OmniCommerce <noreply@omnicommerce.ke>` unless configured. ([nodemailer.adapter.ts](../../../src/server/adapters/email/nodemailer.adapter.ts#L4-L20), [nodemailer.adapter.ts](../../../src/server/adapters/email/nodemailer.adapter.ts#L41-L61)).
- `.env.example` specifies `EMAIL_DRIVER=smtp`, SendGrid host and `qsell` sender, but this is only the example; runtime configuration determines deployment behavior. `NEXT_PUBLIC_APP_URL`/`AUTH_URL` examples point at the public host. ([.env.example](../../../.env.example#L8-L11), [.env.example](../../../.env.example#L61-L70)). `resolvePublicBaseUrl` prefers company-configured public URL then APP/NEXT_PUBLIC_APP/AUTH URL variables and fails in production if none is configured; it uses localhost in non-production. ([account-service.ts](../../../src/server/domains/auth/account-service.ts#L153-L185)).
- The architecture records that registration is open to anyone and invitation is available later as an additional route; it also documents the current 7-day password-reset-token reuse and notification scope. ([vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L132-L139), [vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L900-L908)).

### Inferences

- “Test/demo emails” are not evidenced as hardcoded sample/demo invitation content in the invitation template. More likely source-level explanations are a non-SMTP driver causing the message to appear only in logs, or wrong deployment SMTP/sender/public-URL settings. Actual inbox evidence, runtime `EMAIL_DRIVER`, SMTP provider logs and company `publicBaseUrl` are needed to identify the deployment-specific root cause.
- The account-exists branch prevents a straightforward staff invitation from attaching an existing user to a vendor. That is safe against account enumeration but leaves legitimate existing users without access and without actionable feedback. A deliberately designed “sign in to accept” / verified account association flow is needed rather than silently attaching or disclosing account existence.
- Reusing password-reset purpose makes the token lifecycle work, but couples invite acceptance to general password-reset semantics and future changes to reset policy. A dedicated invitation-acceptance purpose, hashed token, atomic claim, explicit invite status and expiry is clearer and allows invitation revocation and audit independent of password resets.
- A failed SMTP send is swallowed after the user/link and token exist. Without a durable notification outbox, the UI may report success while no email arrives; staff can resend, but send outcome/retry status is not surfaced by this path.

### Gaps

- Repository inspection cannot verify deployed environment variables, live provider configuration, delivery/suppression logs, spam placement, actual message samples, or any production mail route. “Test/demo email” must be confirmed using a received message and its headers plus deployment config/logs.
- No dedicated invitation acceptance page is visible; acceptance is via the generic password-reset page. The exact sign-in redirect/session creation after setting password is supplied by shared auth UI/action and should be traced if implementing a tailored accept experience.

## Can vendors use their portal, and are tenant scoping, permissions and business workflows real or placeholders?

### Takeaway

The assertion that vendors “cannot do anything” is inaccurate for the currently built portal: profile onboarding, bank-change requests, document upload, RFQ response, PO confirmation, supplier invoice/credit flows, payments and team management have server actions/services and meaningful integration/E2E coverage. Some design promises are explicitly deferred, and some delivered screens/actions are narrow/read-only or status-only; distinguish those gaps from the implemented flows.

### Cited Findings

- Public `/vendor/register` renders a registration form; `registerVendorAction` is explicitly open to anyone, rate-limits by IP, creates an unverified vendor user and business, and schedules verification email. Existing verified accounts are left alone, while unverified ones get verification resent. The architecture confirms this self-registration path was a deliberate V-0 design choice. ([app/vendor/register/page.tsx](../../../app/vendor/register/page.tsx), [portal-actions.ts](../../../src/server/domains/vendors/portal-actions.ts#L19-L93), [vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L827-L845)).
- Portal actions run through `portal()` and `requirePortalVendor()`: vendor ID comes from the authenticated session and active `vendor_users`/non-archived vendor lookup, not request input. The runner masks unexpected errors and returns errors as data. ([portal-session.ts](../../../src/server/domains/vendors/portal-session.ts#L10-L21), [portal-access.ts](../../../src/server/domains/vendors/portal-access.ts#L10-L23), [portal-runner.ts](../../../src/server/domains/vendors/portal-runner.ts#L15-L36)). The portal layout independently checks role/vendor session and marks pages noindex. ([layout.tsx](../../../app/vendor/(portal)/layout.tsx#L9-L20)).
- Vendor identity is constrained to one vendor business per user and vendor at most one active owner, with portal access tested for removed users and duplicate association. ([vendors.integration.test.ts](../../../src/server/domains/vendors/vendors.integration.test.ts#L110-L143)); design as-built note says session access rechecked every 60 seconds and `/vendor` guarded. ([vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L827-L833)).
- `portal-isolation.test.ts` is a source-level tripwire ensuring exported portal actions use the runner and do not accept vendor/company/user/actor role as arguments; API upload/download routes must use session guards. ([portal-isolation.test.ts](../../../src/server/domains/vendors/portal-isolation.test.ts#L5-L65)). E2E checks own vendor file access versus other vendor, malformed ID and signed-out access. ([vendor-onboarding.spec.ts](../../../e2e/vendor-onboarding.spec.ts#L104-L123)).
- Profile forms expose save actions for profile, business, directors, references, financial details, contacts, bank-account draft entries and documents. Service guards enforce status/role; ID data and bank numbers are sealed and only masked values are returned. Approved-bank changes use separate controlled flow. ([profile-actions.ts](../../../src/server/domains/vendors/profile-actions.ts#L80-L152), [profile-service.ts](../../../src/server/domains/vendors/profile-service.ts#L190-L197), [profile-service.ts](../../../src/server/domains/vendors/profile-service.ts#L308-L389)). E2E completes all five sections, submits for review, exercises revision/resubmit and file isolation. ([vendor-onboarding.spec.ts](../../../e2e/vendor-onboarding.spec.ts#L12-L102), [vendor-onboarding.spec.ts](../../../e2e/vendor-onboarding.spec.ts#L174-L207)).
- Vendor profile section writes are available only in permitted lifecycle windows: before approval/revision, while review locks editing, and after approval only select maintained details; financial/bank details have bank-change governance. Role/access restrictions are expressed in shared profile policy and service guards. ([profile-actions.ts](../../../src/server/domains/vendors/profile-actions.ts#L27-L36), [profile-service.ts](../../../src/server/domains/vendors/profile-service.ts#L190-L197), [vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L858-L865)).
- Team management is shipped: owner-only invite/resend/remove, finance/sales/read-only roles, active member limit, vendor-scoped membership lookup; invitation tests verify the flow. ([portal-team-actions.ts](../../../src/server/domains/vendors/portal-team-actions.ts#L16-L48), [invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L35-L53), [vendor-controls.integration.test.ts](../../../src/server/domains/vendors/vendor-controls.integration.test.ts#L320-L369)).
- PO list/detail is vendor-scoped, with sent-and-later statuses; confirmation is owner/sales only, checked again in service. ([po-portal-actions.ts](../../../src/server/domains/vendors/po-portal-actions.ts#L13-L27), [po-portal-service.ts](../../../src/server/domains/vendors/po-portal-service.ts#L20-L42), [po-portal-service.ts](../../../src/server/domains/vendors/po-portal-service.ts#L73-L84)).
- Supplier invoices are real portal workflows: vendor role check, PO scope, server totals/validation, own-file scope, invoice submission, recall and close paths. ([invoice-portal-actions.ts](../../../src/server/domains/vendors/invoice-portal-actions.ts#L17-L66), [invoice-portal-service.ts](../../../src/server/domains/vendors/invoice-portal-service.ts#L49-L83), [invoice-portal-service.ts](../../../src/server/domains/vendors/invoice-portal-service.ts#L217-L319), [invoice-portal-service.ts](../../../src/server/domains/vendors/invoice-portal-service.ts#L321-L349)). Credit memo and payment portal action/service modules are also present (e.g. `credit-memo-portal-actions.ts`, `payment-portal-actions.ts`); RFQ has list/detail/respond/quote/decline flows (`rfq-portal-actions.ts`, `rfq-portal-service.ts`).
- Notifications exist for onboarding, bank changes, document expiry, RFQs, PO sent/amended/confirmed, invoice and credit status, and payment remittance in `VendorNotifier`; all route links are configuration-based. This is an email service/template implementation, not a vendor in-app communication inbox. ([notifier.ts](../../../src/server/domains/vendors/notifier.ts#L65-L184), [notifier.ts](../../../src/server/domains/vendors/notifier.ts#L233-L383)).
- The architecture explicitly flags incomplete items: no country-pack tax-ID pattern; callback verification is a human action recorded by staff; no per-user mail subscriptions/notification centre. ([vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L900-L916)). More deferred lifecycle/approval behavior is described in the plan and as-built sections; documentation can lag code, so current source and tests take precedence for exact shipped behavior.

### Inferences

- The portal has meaningful capability but not every vendor role can do every action: `readonly` is view-only; finance/sales permissions are segmented; state and approval gates intentionally disable editing. Users may interpret those controls as “nothing works” if onboarding is not complete, their invitation is pending, they are signed in under the wrong address, or no PO/RFQ/invoice has yet been sent to their vendor.
- The permission model’s vendor-user role is a fixed domain capability set rather than staff RBAC. Most sensitive writes have service-level role checks plus ownership scope. Keep reviewing new route/actions against the isolation guard because the guard is a static source check, not a proof of every downstream query.
- There are operational/product completeness differences: portal communications are email + histories/status pages rather than two-way messaging; PO offers confirm but not edit; invoicing is PO-based, while design describes some free-line/expense-vendor cases not shown as universally enabled. Do not advertise a generic fully open profile editor for approved vendors.

### Gaps

- The repository alone cannot explain the particular user’s symptom without their URL, sign-in identity, vendor status, membership role/status, browser error and action result. Check `vendor_users`, `users.role/isActive/emailVerifiedAt`, vendor status/block, and relevant vendor event history before diagnosing an individual account.
- This audit did not execute the complete test suite or each portal journey; findings report code and committed test coverage, not current pass status. The working tree was already heavily modified before audit; no changes from those pre-existing modifications were inspected or made.

## What are the exact implementation risks and the secure invitation-led plan?

### Takeaway

The principal mismatch is policy, not missing invitation machinery: `/vendor/register` is public and intentionally creates vendor businesses, while invitation is an additional entry path. For an invitation-led product, retire public vendor business registration while preserving staff-created vendor records and invite acceptance. Address invitation reliability and existing-account association with explicit invitation records and durable delivery rather than relying on a password-reset token plus swallowed send errors.

### Cited Findings

- Public self-registration is named as the only public portal action in the isolation-test allowlist; it validates inputs and rate-limits by IP but remains a public business creation endpoint. ([portal-isolation.test.ts](../../../src/server/domains/vendors/portal-isolation.test.ts#L10-L15), [portal-actions.ts](../../../src/server/domains/vendors/portal-actions.ts#L19-L43)). The architecture currently calls this open-to-anyone registration intentional. ([vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L832-L845)).
- Staff invitation is authorized through admin action infrastructure/`vendors:invite`; colleague invitation authorizes owner in both action and service. ([admin-actions.ts](../../../src/server/domains/vendors/admin-actions.ts#L64-L90), [portal-team-actions.ts](../../../src/server/domains/vendors/portal-team-actions.ts#L24-L48), [invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L61-L83)).
- The invitation creates the user first and vendor link/event transaction second; cleanup handles link transaction failure. Mail/token issuance occurs after that transaction, and the notifier catches email send failures. This creates a persisted pending account without a durable queued delivery result if SMTP fails. ([invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L42-L59), [notifier.ts](../../../src/server/domains/vendors/notifier.ts#L31-L48)).
- Member-count and staff “no active owner” checks are ordinary reads before writes; absent a demonstrated database constraint/locking strategy in this path, concurrent invite requests can race those business rules. Existing as-built docs report a partial unique active-owner index, but count cap may still require serialization/constraint. ([invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L35-L47), [vendor-management-module.md](../../../docs/architecture/vendor-management-module.md#L831-L833)).
- A new token revokes all outstanding tokens for that user/purpose; because invitation uses `password_reset`, issuing a reset email for the same user could invalidate the invite link and an invite resend can invalidate an unrelated password-reset link. ([token-repository.ts](../../../src/server/domains/auth/token-repository.ts#L34-L51), [invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L56-L59)).
- Existing-address invitations silently do nothing; no invitation or vendor-user row is created. This avoids disclosure but does not support the legitimate use case of adding a pre-existing account to a vendor business. ([invitation-service.ts](../../../src/server/domains/vendors/invitation-service.ts#L40-L43), [vendor-controls.integration.test.ts](../../../src/server/domains/vendors/vendor-controls.integration.test.ts#L337-L345)).
- Deployment email default mismatch is material: source defaults to console, while `.env.example` opts into SMTP. A production deployment lacking `EMAIL_DRIVER=smtp` will log invitation payload snippets instead of delivering mail. SMTP sender default can also differ from `qsell`; actual runtime values must be verified. ([container.ts](../../../src/server/di/container.ts#L310-L321), [nodemailer.adapter.ts](../../../src/server/adapters/email/nodemailer.adapter.ts#L4-L20), [.env.example](../../../.env.example#L61-L70)).

### Inferences

- Primary risks: unsolicited/fraudulent self-created vendor records and review workload; orphaned/pending vendor identities on delivery failure; confusion or cross-purpose token invalidation; inability to invite an existing account; staff-owner invite race; email misconfiguration that appears successful but prevents onboarding. Tenant disclosure/IDOR risk is materially mitigated by session-derived vendor scope and is backed by isolation tests, but remains a high-impact invariant to preserve.

### Gaps

- No deploy configuration, runtime logs, monitoring, SMTP provider dashboard or prod database was inspected; cannot confirm whether the shipped environment has console driver, a sandbox provider, broken DNS/credentials, sender-domain issue or misdirected base URL.
- The complete `users`/`vendor_users`/`auth_tokens` schema constraints and current migration history should be reviewed before implementing the concurrency/uniqueness changes; audit identified the architecture’s stated constraints but did not propose a schema migration from incomplete direct table review.

### Secure invitation-led implementation plan

1. **Set the entry policy.** Remove `/vendor/register` from public navigation/proxy allowance and stop `registerVendorAction` from creating vendor businesses. Keep `/vendor` login, a private invitation-accept route, and staff creation of vendor records. Existing active registrations remain; offer an explicit migration/invite path rather than deleting accounts. Keep self-registration only if product later deliberately opts back in.
2. **Model invitations explicitly.** Add a `vendor_invitations` record: vendor/company, normalized target email, intended role, inviter, created/expiry/accepted/revoked timestamps, state, invitee user id nullable, hashed random token, and idempotency/unique constraints. Do not store plaintext token. Keep history/audit event records. Define uniqueness and replacement semantics (one active invite per vendor+email; explicit resend revokes/replaces) in database constraints and transaction boundaries.
3. **Separate acceptance from reset.** Introduce an `invitation_acceptance` token purpose or invitation-specific token table. Atomic consume/accept transaction validates expiry, not-revoked state, exact normalized email and vendor status; for a new user, set password and verify email, create/activate the `vendor_users` link and mark invitation accepted atomically. For an existing account, require that the signed-in account matches the invited email and explicit accept; do not reveal account existence to anonymous callers. Treat role changes and vendor association as auditable actions.
4. **Make creation/delivery recoverable.** Insert invite and durable notification/outbox row in one transaction; worker delivers/retries with bounded backoff and idempotency, records provider/message/error state, and exposes pending/failed/resend state to authorized staff. Never return a false “sent” confirmation when only queued or failed. Add an operational health check that fails deployment/readiness for a production console driver and missing SMTP sender/host/public URL; retain console only for local/test and redact token/body from normal logs.
5. **Harden concurrency and lifecycle.** Lock vendor row while enforcing member cap/owner constraints or use appropriate DB constraints; preserve one active owner. Ensure cancellation/revocation disables pending link and user if not shared; removal revokes sessions/tokens and access immediately or by documented short cache bound. Define owner transfer/recovery and invitation expiry cleanup. Rate-limit invite/resend per actor/vendor/IP and return enumeration-safe responses.
6. **Verify email/environment end-to-end.** Check live `EMAIL_DRIVER`, SMTP host/port/auth, `EMAIL_FROM` domain, `APP_URL`/company `publicBaseUrl`, TLS and provider accepted/rejected events; verify SPF/DKIM/DMARC and links in a staging mailbox. Use branded `qsell`/tenant content; use separate non-production mail sink/allowlist for dev/staging so real supplier addresses never receive test notifications.
7. **Preserve and verify portal invariants.** Keep session-derived `vendorId`, server-side role/status authorization, record-level vendor predicates, file ownership checks, noindex/private metadata and masked errors. Review each action/service for exact role and state transition, especially bank account changes and document reads. Ensure pending invitation users cannot log in before acceptance, unverified user cannot sign in, and archived/removed users are denied.
8. **Build tests and documentation with the change.** Unit tests: token lifecycle, expiry/revocation, normalized emails, role matrix, safe response. DB integration/API: atomic one-time accept, same email/existing account, parallel accept/resend/owner invites, cap/owner constraints, cancellation, tenant IDOR and audit/outbox retries. E2E desktop/mobile: staff-created vendor → owner invite → email link → password/accept → portal login; owner colleague invite; expired/revoked/reissued link; existing account; SMTP failure/retry and environment config. Update architecture sections 5.2, as-built notes, deployment/env docs, admin/owner help and support runbook. Retain full suite per project rules (unit, integration, API and e2e).
